# Authoring the reader

Everything a new session needs to keep writing readings without rediscovering
the constraints. This is the **reference**; the work is done through **one
skill, `/author`**, which routes to the right process and leans on this doc and
on [`WORD-TYPES.md`](WORD-TYPES.md):

| call | does |
|---|---|
| **`/author`** | write a new reading end to end — target, write, annotate, gate |
| **`/author fix`** | clear the backlog — fix wrong tags (lint) and fill missing tags |
| **`/author audit`** | check the schema itself against grammar (Kāle) and the corpus |

The three are one door because they share the laws and the reference, but the
processes differ: authoring *adds* correct material, fixing *repairs* existing
annotations against the schema, and auditing *changes the schema* when it is
wrong. A lint finding that is really a schema gap moves from the first two to the
third — never force a wrong tag to silence the lint. (The detailed Fix and Audit
processes live in `.claude/skills/fix-annotations/` and `.claude/skills/audit-schema/`.)

Two laws sit under all three: **`bun run lint` is a hard gate at zero** (a wrong
annotation fails the build), and the **Vedic (Ṛgveda) block is frozen** (see the
callout in "The chapters" below). The rest of this doc is the detail the skills
cite.

## The one command

```bash
bun run check
```

Runs every corpus check and exits non-zero on the two that are always errors.
Run it before and after any authoring batch.

```
✓ gloss/token: 48  (baseline 48)      hard — any INCREASE fails
✓ सङ्ग्रह constraint: clean            hard — a passage may not introduce a rule
· coverage: 42/131 load-bearing rules taught
· revealed: 30% of the corpus shown by default, 42% in late attested
· teaches: median 78 chars, 0 line(s) over 240
· register: 25 term(s) used before introduction
· citations: 80 confirmed against vidyut, 39 to review
```

The soft lines are candidate lists, not failures. `register`'s 25 are mostly
terms glossed inline in the same sentence — read before rewriting.

Other commands: `bun run ledger` (coverage detail, `--full` for every rule),
`bun run verify:cites`, `bun run check:register`, `bun run build:readings`.

## Where things live

| | |
|---|---|
| authored source | `content/readings/<chapter>/<id>.yaml` — one file per reading, **edit these**, never the JSON. Open a reading by its id with your IDE's "Go to File" (e.g. `ku0101`). |
| the plan | `content/readings/_syllabus.yaml` — conventions in its header |
| the target set | `content/readings/_rules.yaml` — load-bearing vs leaf |
| **the annotation contract** | **[`WORD-TYPES.md`](WORD-TYPES.md)** — every kind of word and what each must be tagged for |
| built payload | `static/data/readings.json` — generated, committed |
| quiz cells | `static/data/quiz-cells.json` — generated by vidyut, committed |

**This reader teaches every part of speech, not only nouns.** Verbs (तिङन्त),
primary derivatives (कृदन्त), secondary derivatives (तद्धित), compounds (समास),
pronouns (सर्वनाम) and indeclinables (अव्यय) each have their own dimensions and
their own authoring obligation. [`WORD-TYPES.md`](WORD-TYPES.md) is the full
inventory — read the row for a word's type before annotating it, because a
सुबन्त, a तिङन्त and a कृदन्त do not carry the same tags. It is also code
(`src/lib/usage/schema.ts`), so `bun run complete` checks the corpus against it;
the "Grammatical completeness" section below is the working summary.

`bun run build:readings` after every edit. `bun run build:quiz` only when the
corpus gains new *words* — it is a three-pass chain (readings → cells →
readings) because the cells are derived from the corpus's own forms.

### Why the quiz is derived, not tagged

`build-quiz.ts` asks vidyut which `(linga, vibhakti, vacana)` cells produce
each surface form. Of 472 forms:

| cases the form can be | forms |
|---|---|
| 1 — the form settles it | 287 |
| 2 | 94 |
| 3 | 66 |
| 4-5 | 25 |

**185 forms are ambiguous**, and 25 are four- or five-way. पादाभ्याम् is
तृतीया / चतुर्थी / पञ्चमी; नरौ is प्रथमा / द्वितीया / सम्बोधन. The first
version of the quiz read the answer off the word's `term` tags and asserted one
case for all of them — so it marked correct answers wrong, and contradicted
itself (फलम् asked as प्रथमा in ex182 and द्वितीया in ex008).

Where the form cannot settle the case, the quiz shows the **phrase** that does
and draws its distractors from the other cases that form can actually be. Do
not add hand-written case answers; extend the derivation instead.

## How coverage moves

A rule counts as taught at **8 distinct readings**. A story is one reading, so
it adds one encounter per rule no matter how often the rule appears in it.
Choosing *which* rules is the whole lever.

The pattern that works, proven twice (28→35, then 36→37):

1. a **सङ्ग्रह passage** that lifts a cluster of rules to 7/8
2. a **story** that touches each of them once more, and they cross together

Pick targets from `bun run ledger`'s partial list, not by tier order.

**Before authoring against a low number, check whether it is a tagging gap.**
Four "gaps" this session turned out to be measurement errors: शप् had 118
readings containing a present verb and 2 citing it; the कारक role terms were
mapped to the wrong sūtras; 8.3.23 had 32 matching words and 3 citations. The
ledger has been wrong in the same direction repeatedly — undercounting what the
corpus already teaches.

## Introducing a word costs less once its cell is taught

A cell is a `(stem-class × विभक्ति × वचन)` slot — आकारान्त feminine in
प्रथमा एकवचन, अ-stem masculine in षष्ठी बहुवचन, and so on. The first word to
occupy a cell **has to be introduced**: a short reading whose whole job is to
show that सेना takes आ in the nominative, that रामस्य ends षष्ठी. That reading
carries the `cite` and the full apparatus, and the cell is now taught.

**Every later word in that same cell is not a new grammatical fact.** Once
प्रथमा-एकवचन-आकारान्त is established by सेना, the words कन्या, लता, माला,
गङ्गा inflect identically — they are *vocabulary*, not grammar. They do not
need their own introductory sentence. Drop them straight into a larger passage,
glossed for meaning only (`gloss` + a bare identity `term`, **no `cite`**), and
let the reader recognize the ending they already know on a word they do not.

This is the same recall-first principle the सङ्ग्रह chapter runs on, applied
one level down: there, a *rule* met earlier becomes scenery; here, a *cell* met
earlier lets a new lemma enter as scenery. The two compound — a passage that
consolidates four rules can also be where six new lemmas first appear, so long
as every ending on them belongs to a cell already taught.

**What decides whether a word needs its own reading:**

| the word introduces… | how it enters |
|---|---|
| a new cell (first आकारान्त fem., first इ-stem dative) | its own short reading, full apparatus, `cite` |
| only new *meaning* in a taught cell | mid-passage, `gloss` + identity `term`, no `cite` |
| a new cell **and** carries the passage's theme | may headline a passage that also drops in taught-cell words |

The failure mode this prevents is the corpus filling with near-duplicate
introductory sentences — सेना गच्छति, कन्या गच्छति, लता गच्छति — each spending a
full reading to teach a cell that the first one already taught. That is padding,
not coverage; the ledger does not move, and the reader re-reads the same fact.
When you catch yourself about to author "X does Y" where X is a fresh lemma in a
cell some earlier reading already owns, put X in a passage instead.

**The check on this is the register pass.** A word entering mid-passage still
must not use a *cell* the reader has not met — that would be introducing grammar
without teaching it, the same fault the सङ्ग्रह constraint catches for rules.
`bun run check:register` flags a term used before its introduction; treat a new
lemma whose ending belongs to an untaught cell the same way.

## The chapters

`12_sangraha.yaml` holds consolidation passages. Its header carries five
authoring rules; the load-bearing one is **a सङ्ग्रह passage introduces
nothing** — every rule it cites must already appear at or below its tier. The
check enforces this and has caught violations twice, both from mechanical edits.

`09_katha.yaml` is graded narrative, `06_readings.yaml` is attested text.
Attested is 30 Ṛgveda / 8 Hitopadeśa / 3 Pañcatantra — the Ṛgveda block from
tier 280 up is a wall, and classical prose between the subhāṣitas and the hymns
is where the corpus is thinnest.

> **The Vedic (Ṛgveda) material is FROZEN — do not extend or deepen it.** The
> text of RV 1.1 was verified akṣara-for-akṣara against an independent reference
> (Detlef Eichler's accented saṃhitā) and is faithful. But we have **no reliable
> source** that gives, in one place and machine-checkable, the accented text
> *and* the per-word morphology — so two Vedic-specific layers cannot be verified
> to the standard the rest of the corpus meets:
>
> - **Accent positions** (which syllable is उदात्त/स्वरित). The text matches; the
>   *svara marks* were never verified against a padapāṭha, because the reference's
>   accent encoding needs a separate position-by-position check we have not run.
> - **Vedic moods** (लेट् subjunctive, the injunctive). The schema now *has* लेट्
>   (Kāle §3, 3.4.7), and the existing tags are our best reading — but a wrong
>   mood on an archaic form would not be caught by any check, since vidyut targets
>   Classical and cannot confirm a Vedic form.
>
> So: leave the 9 existing ṛcs as they are, keep the accents verbatim from the
> source, and **do not add new Vedic readings or new accent/mood annotations**
> until we have a canonical accented + morphologically-tagged Ṛgveda (VedaWeb /
> the van Nooten–Holland edition) to verify against. Everything else — the graded
> and classical-attested material — is fully checkable and open for authoring.

## Register — the part checks cannot catch

Four separate passes fixed prose faults, and the user caught every one of them
before the tooling did. The rules are recorded in `_syllabus.yaml`; the ones
that keep recurring:

- **`teaches` length.** Corpus median 78 characters. Lines authored later
  reached a median of 260 by narrating what a passage is *for* rather than
  naming what is in it. Now warned at 240.
- **A closing paragraph that restates the opening.** Invisible in isolation —
  the paragraph reads fine until you set it beside the one above.
- **Explaining the method, not the Sanskrit.** "That difference is what
  consolidation means", "already met", "one at a time". The reader does not
  know the corpus exists.
- **Shouty caps, `+`-chained feature lists, corpus-internal references**
  ("minimal pair with ex122" — the reader has no ids).

Say what is on the page and stop.

## Numbering

`segment` is the difficulty tier, in **tens** (10, 20, … 570), with the nine
slots between free for insertions. `id` is authoring order and nothing else —
it disagrees with pedagogical order on a third of pairs. Never renumber ids.

## Grammatical completeness — what every word needs

**[WORD-TYPES.md](WORD-TYPES.md) is the full inventory** — every kind of word in
the language, the dimensions each is annotated along, and which of those must be
authored versus derived. What follows is the working summary.

A word's `notes[]` are not decoration. Three things read them: the reader's
rail, the quiz builder, and the प्रयोग index. A missing tag does not degrade
gracefully — it removes the word from a paradigm, or produces a question with
no answer.

**What the rail shows below the quiz, by word type.** When a word is selected,
the rail shows its gloss, terms and sūtras — and then one structural exhibit
chosen by what the word *is*:

- a **सुबन्त / तिङन्त** gets its **paradigm grid** (declension or conjugation)
  with its own cell lit — resolved from the four table readings (देव, फल, नदी,
  भू), see `src/lib/reader/wordParadigm.ts`.
- a word that sits in **no grid** — a समास, a कृदन्त/तद्धित, a plain सन्धि join —
  gets a **decomposition strip** instead: the compound's विग्रह (राजपुरुषः →
  राज्ञः पुरुषः), the derivative's affix chain (गम् + त → गतः), or the sandhi
  split (वाक् + अत्र). This is `src/lib/reader/wordDecomp.ts`, and it **parses
  your free text** — so the shapes it keys on now matter:
  - a compound's `text` note must lead with `विग्रह: <analysis>` — the analysis
    is read up to the first `—` or `;`, so put the Devanagari members first and
    any English gloss after a dash.
  - a कृदन्त/तद्धित's citation `role` should spell the chain and end in the form:
    `… → base + affix → form` (as ex218's तृच्/त्व/मतुप् roles do). The strip
    extracts the `X + Y → Z` tail; a role with no arrow yields no strip.
  - a सन्धि note's `en` or `text` should contain the split as `A + B`.

  A note the parser cannot read yields no strip — the terms and cites still carry
  the fact — so this never shows a mangled analysis. But an author who keeps the
  shapes above gets the exhibit for free, which is the point.

**The rule: name the word's type, then every feature that type inflects for.**
The type tag is what tells the tooling which paradigm the word belongs to;
the feature tags are the coordinates within it. One without the other is
unusable.

### The schema — what you author, per type

**Author the left column. Never author the right one** — it is filled in at
build time from the derivation, and a hand-written copy goes stale silently.

| type | you author | filled in for you |
|---|---|---|
| **सुबन्त** | `lemma` · विभक्ति · कारक (when the sentence assigns one) | वचन · लिङ्ग |
| **सर्वनाम** | `lemma` · विभक्ति | वचन (लिङ्ग is the referent's, not the word's) |
| **तिङन्त** | `lemma` · लकार · प्रयोग · उपसर्ग · सनादि | पुरुष · वचन · पद · गण |
| **कृदन्त** | `lemma` · the कृत् suffix · **विभक्ति if it declines** | वचन · लिङ्ग |
| **तद्धित** | `lemma` (the प्रकृति) · the suffix · its अर्थ · विभक्ति | वचन · लिङ्ग |
| **समास** | `lemma` · समास type · विग्रह · विभक्ति | वचन · लिङ्ग |
| **अव्यय** | `lemma` · the subtype | — nothing inflects |

The rule behind the split: **author what the sentence or the analysis decides;
let the engine supply what the form determines.** विभक्ति is authored because
देवे could be five cells and only the sentence says which; वचन is derived
because once the stem and the case are known, the form settles it.

**Name the specific tag, not the category.** `कृदन्त` says a word is a primary
derivative; `क्त` says which one, and only the second tells the reader whether
it declines. The corpus currently has कृदन्त 62× against क्तवतु 1×, तद्धित 13×
against अपत्य 1× — the generic label beating the specific one everywhere.

**Every word needs a `lemma`.** It is the one thing nothing can derive: a word
with no stem belongs to no paradigm, and 144 words are invisible to प्रयोग for
exactly this reason.

`cite` is separate from all of this — it records which sūtra produced the form
and is the only tag `verify:cites` can check. Not required, but a form with a
non-obvious derivation and no citation is a missed teaching opportunity.

The full inventory, with every subtype and its atomic values, is in
[WORD-TYPES.md](WORD-TYPES.md).

### Where the corpus stands

Measured over 2,301 annotated words:

| | count | type tag | features complete |
|---|---|---|---|
| सुबन्त | 1,242 | 100% | **वचन 5%**, कारक 50% |
| तिङन्त | 369 | 100% | **पुरुष 4%, वचन 4%, पद 1%** |
| कृदन्त | 106 | 100% | **विभक्ति 0%, वचन 0%** |
| अव्यय | 293 | 100% | — |
| **untyped** | **291** | **—** | see below |

The vertical axis is nearly complete and the horizontal one is nearly empty.
Every word says what it is; almost none say which cell it occupies.

The 291 untyped words break down as:

- **101** carry a पुरुष or वचन but no लकार — a verb whose head tag is missing.
  गच्छामि is tagged only उत्तमपुरुष, so nothing knows it is a verb.
- **22** carry a कारक role but no विभक्ति — गोकुले is tagged अधिकरण alone.
- **153** carry only incidental tags (सन्धि, उपसर्ग, a root name, सर्वनाम).
- **15** carry no `term` tag at all.

### What is derived, and what you must still write

`bun run build:quiz` asks vidyut which `(liṅga, vibhakti, vacana)` cells produce
each form, so **वचन is recovered for सुबन्त without being authored**. That is why
the प्रयोग grid has a second axis at all. Do not read this as permission to skip
the tag:

- Derivation gives the *candidates*, not the answer. देवे is five cells until the
  annotation's सप्तमी narrows it to one. Filling cells from candidates alone put
  कूपे in five places and made half the grid speculation.
- **पुरुष, वचन and पद ARE derived for a तिङन्त** — vidyut settles them from the
  form, and the build writes them into `derived`. **गण and विकरण are derived too**,
  keyed on the lemma from the dhātu table (भू → भ्वादि · शप्); अदादि/जुहोत्यादि
  have a गण but no शप्-like विकरण, so विकरण is `optional`. Only लकार stays
  authored — it is not recoverable from the form (गच्छति vs गच्छतु share a stem).
- **विभक्ति is derived from the कारक role as a fallback.** A word tagged कर्मन्
  with no विभक्ति gets द्वितीया in `derived` (the role's default case, 2.3.x) —
  the author's own assertion, never overriding a written विभक्ति. This is why a
  कारक-only word now types and completes without its विभक्ति hand-written.
- Gender is an input to derivation, never an output. It is narrowed by scoring
  the liṅgas that produce the attested forms in their annotated cases — which
  works only when the cases are annotated. For a सर्वनाम, लिङ्ग is the referent's
  and `optional` — a pronoun owes no gender of its own.

**Vedic accents are display data.** दे॒वेषु॑ and देवेषु are one word for every
lookup: vidyut emits no accents and cannot parse them. The build deaccents on
the way in. Write the accent where the source has it; never rely on it matching.
(And per the freeze above, do not author *new* accents — the existing ones are
verbatim from a verified source; new ones cannot be checked.)

### The rule of thumb

Before saving a word, ask what a reader would have to know to place it in its
paradigm — and check that the tags say all of it. If a तिङन्त says only "लट्",
it is a present-tense *something*. If it says लट् · प्रथमपुरुष · एकवचन ·
परस्मैपद, it is a cell.

## How a reading reaches the app

One rule governs the whole chain: **the YAML is the only thing written by hand.**
Everything downstream is derived, and any fact that appears in two places will
eventually disagree — that is what produced the फलम् quiz contradiction and the
कूपे-in-five-cells grid.

```
content/readings/<chapter>/<id>.yaml   ← you write this, and nothing else
                                         (one file per reading; NN_name/ = chapter,
                                          <id>.yaml = a bare one-item sequence)
        │
        │  bun run build:readings        (pass 1 — no quizzes yet)
        ▼
static/data/readings.json
        │
        │  bun run build:quiz            (vidyut: derives cells)
        ├──────────────► static/data/quiz-cells.json   what a FORM can be
        └──────────────► static/data/usage.json        what the CORPUS attests
        │
        │  bun run build:readings        (pass 2 — quizzes, now that cells exist)
        ▼
static/data/readings.json  ──►  /reader  /usage  /review
```

`bun run build:quiz` runs all three passes. The loop is deliberate: the quiz
needs the cells, and the cells are derived from the corpus's own forms.

### The one command, and when

| after you… | run |
|---|---|
| edit any `content/readings/<chapter>/<id>.yaml` | `bun run build:readings` |
| add or change **words** (new forms, new lemmas, new tags) | `bun run build:quiz` |
| anything, before pushing | `bun run check` then `npm run build` |

### Authoring a reading, end to end

```bash
# 1. write it — content/readings/NN_chapter/<id>.yaml (one reading per file,
#    as a bare one-item sequence: the file begins `- id: <id>`)
# 2. see it
bun run build:readings

# 3. check what the words still owe
bun run complete --reading ex212

# 4. fill the gaps, rebuild, and let the derived data catch up
bun run build:quiz

# 5. the gate
bun run check && npm run build
```

`bun run complete` is the tool for step 3. It reads the completeness spec above
and says, per word, which tags are missing:

```
ex209 — 33 word(s) underspecified
  दूतः      सुबन्त   needs वचन
  अगमत्     तिङन्त   needs पुरुष, वचन, पद
```

- `--worst 20` ranks the readings by how much they are missing — the queue.
- `--untyped` lists words carrying no type tag at all, which are invisible to
  every downstream view.

Completeness never fails the build. The backlog is deep and blocking on it would
make the command useless; `bun run check` prints the headline counts so the
number cannot quietly grow while nobody is looking.

**Correctness does fail the build.** There are four ways an annotation can be
wrong short of being missing, and all are always errors:

- a **conflict** — two values of one dimension, only one of which can be true
  (लट् *and* विधिलिङ् on one verb; प्रथमा *and* द्वितीया on one noun);
- a **misplaced** tag — a value that is no dimension of the word's type (a
  विभक्ति on a finite verb, a पुरुष on a plain noun that should be a सर्वनाम);
- a **wrong-lemma** — a word filed under a closed type whose lemma is not one of
  its stems (सर्व tagged सर्वनाम, when सर्व is a सर्वादि);
- a **bad-relation** — a `rel[]` edge that does not hold (below).

`bun run lint` (= `check-complete.ts --lint`) reports these, and `bun run check`
runs it as a **hard gate** beside the सङ्ग्रह and gloss/token checks. The corpus
is at **zero**, so any new one fails the build the way a सङ्ग्रह violation does.
This is the enforcement the completeness report never was: missing is a backlog
you chip at, but wrong is caught the moment it lands.

### Relations — `rel[]`, the edges between words

Most annotation is per-word, but agreement, government and compound-membership
are edges *between* words, so they go in a `rel[]` array (see WORD-TYPES.md §6):

```yaml
- form: धनवान्
  rel:
    - kind: विशेषण    # I qualify …
      to: 0          # … word index 0 in this reading's words[] (राजा)
```

`to` is the 0-based index into the same reading's `words[]`. The lint checks each
edge — unknown `kind`, `to` out of range or self-pointing, a source type that may
not carry the edge, or an `agree` axis (लिङ्ग/विभक्ति/वचन for विशेषण) that
disagrees when both ends state it. The build preserves `rel[]` untouched; author
it in the YAML like `notes`.

When the lint flags a word, it is usually one of three things: a genuine mistag
(fix the tag), a word that needs its type marker (अहम् tagged उत्तमपुरुष but not
सर्वनाम — add सर्वनाम), or a real gap in the schema (the tag is correct and the
type should carry that dimension — add it to `schema.ts`). All three were real
in the first pass; the lint is how you tell them apart.

`npm run build` does **not** regenerate the derived data. `quiz-cells.json` and
`usage.json` are committed artifacts, like the readings themselves — rebuild
them deliberately, inspect the diff, commit it with the reading that caused it.

### What each stage is allowed to decide

The split matters, and getting it wrong is how the grid filled with speculation:

- **The YAML asserts.** This word is सप्तमी. This verb is लङ्. These assertions
  are evidence and are never overridden by the engine.
- **vidyut supplies what the annotation cannot.** वचन for a सुबन्त; पुरुष and वचन
  for a तिङन्त; the unattested cells of a paradigm. It answers *"what could this
  form be?"* — a candidate set, not a fact.
- **The build intersects them.** Annotation narrows the engine's candidates to
  the cell the sentence actually uses. Where the corpus is silent, the कारक role
  stands in (अधिकरण → सप्तमी). Where both are silent, the cell stays ambiguous
  and says so.

Never let a derived value overwrite an authored one, and never let a candidate
set masquerade as an answer. When the two disagree — they never have, across
507 noun forms — trust neither silently; surface it.

### What the app reads

| surface | reads | shows |
|---|---|---|
| `/reader` | `readings.json` | the reading, its glosses, the quiz gate |
| `/usage` | `usage.json` | the paradigm grids, attested and unattested |
| `/ref/[id]` | commentary data | the sūtra — joined *from* प्रयोग by citation, never the reverse |

The join is one-way and cheap: a प्रयोग cell cites `7.1.12` and links to
`/ref/7.1.12`. Nothing under `/ref` knows प्रयोग exists.

### Adding a new category

The section shape is generic on purpose. सुबन्त is विभक्ति × वचन and तिङन्त is
पुरुष × वचन with लकार pinned; both are the same object with different axes
declared in the data. A new grid — सन्धि as final वर्ण × initial वर्ण, वर्णमाला as
place × manner — should be **a new index section, not a new renderer**. If you
find yourself adding a case to the page component, the axes probably belong in
the data instead.

Categories that are *not* grids — कारक, समास, कृदन्त, तद्धित — are typologies:
their members are told apart by a question, not by coordinates. They stay in
`/ref/tables` until they get an exhibit of their own.

**सर्वनाम is its own section, not a class inside सुबन्त.** It takes सुप् endings,
but the endings differ — तस्मै where a noun has देवाय, तस्मिन् where a noun has
देवे — under rules that apply to pronouns alone, and one lemma carries three
genders where a noun carries one. Filing it under सुबन्त put a three-gender word
in a list keyed by gender. The tradition keeps it apart and so does
`/ref/tables`.

The browse taxonomy lives in `src/lib/usage/taxonomy.ts`, lifted from the
section structure `/ref/tables` already carries: अकारान्त, आकारान्त, इ/उकारान्त,
ऋकारान्त, हलन्त for nouns; गण for verbs; प्रकार for pronouns. Taking it rather
than deriving from spelling matters — तद् and यद् are द्-final and a spelling
rule files them beside राजन्, which is not how anyone learns them.

## Known gaps

- **39 citations to review** (`bun run verify:cites --full`). Mostly consonant
  stems vidyut cannot derive from the recorded lemma, and तद्धित rules that
  fire during stem formation. Checker limits, not corpus errors.
- **48 gloss/token mismatches** — unglossed यः/सः in ex161-165, label prefixes
  in ex038-040 and ex174-178. Real authoring gaps, listed by the build.
- **3 rules never cited**: 1.2.43, 7.3.86, 8.4.1.
- **Feature tags are the biggest gap in the corpus.** 95% of सुबन्त carry no
  वचन, 96% of तिङन्त carry no पुरुष, and 291 words carry no type tag at all.
  Derivation now covers both — वचन for nouns, पुरुष and वचन for verbs — so both
  प्रयोग grids exist. But **the reader's rail still shows only the authored
  tags**, so सभाम् displays as "कर्मन् · द्वितीया" with no वचन. The derived cell
  is available and unused there. See "Grammatical completeness" above.
- **45 verb roots are not in the dhātu table** (78 occurrences), so their forms
  are skipped by प्रयोग: ज्वल्, कथ्, त्यज्, पा, ग्रह्, धृ… A root needs its
  aupadeśika spelling and gaṇa, and a wrong gaṇa silently derives a different
  verb — so each addition must be checked against a form the corpus uses, not
  guessed. The build prints the unmapped list every run.
- **The quiz still asks the unanswerable question.** 720 of 1,480 quizzes ask
  "which विभक्ति?", resting on the engine's judgment that the form settles it;
  307 more ask it of forms that are genuinely ambiguous, with the phrase shown.
  380 cells now resolve to exactly one answer, which is what a fill-the-cell
  question would need — show the cell, ask for the form. Unbuilt.
- **144 words have no `lemma`**, mostly ex001-ex004. They cannot be indexed by
  प्रयोग at all — a word with no stem belongs to no paradigm.
- **`/review` is reachable only from the home page**, not from the site nav,
  so a reader who banks a word from the rail has no obvious way back to it.
  The design puts review beside the text rather than on its own page — a card
  in the rail was started and backed out, because it duplicated the page that
  already exists. Unresolved: either the nav gains the pillar, or the rail
  gains the card and `/review` goes.
- **The quiz gate and the recall-first token display overlap** — both make the
  reader try before seeing the gloss. The design has both; whether they should
  both stay is unsettled.
